# 03 - 变体系统：双刃剑与治理

## 1. 为什么会有变体

GPU 着色器里不能用"动态 if"吗？可以（第02章讲过分支的代价），但**把可能的分支提前编译成多个版本**往往更快——版本间没有分支开销，寄存器分配更优。

于是团结/Unity 提供了编译期开关：**关键词**。

```
#pragma multi_compile _ _FOG_ON
...
#ifdef _FOG_ON
    color = MixFog(color, fogCoord);
#endif
```

带 `_FOG_ON` 与不带，各编译一份——**2 个变体**。关键词在材质面板（勾选）/全局（引擎按场景状态）开启。

变体的本质：

> **变体 = 同一 shader 源码对"每个关键词组合"各编译一份的产物。变体总数 = 所有 multi_compile 维度大小的连乘积。**

$$
V = \prod_i |K_i|
$$

## 2. multi_compile vs shader_feature：行为差异

两条声明指令，编译行为一致，**包含与剔除规则**不同：

| | `multi_compile A B` | `shader_feature A` |
|---|---|---|
| 变体打包进包 | **全部**（不可剔除） | **只打"被使用过"的**（未用过的默认剔除） |
| 打开某关键词的途径 | 脚本 `EnableKeyword` / 引擎全局 | 材质勾选 / 脚本改材质 |
| "被使用"如何感知 | 不需要（全量） | **要记录**：材质面板操作 / variant collection / 场景扫描 |
| 典型用途 | **引擎管的**（FOG、LIGHTMAP、SHADOW、INSTANCING...） | **玩法管的**（我的剑要发光 `_GLOW`） |

**误用事故 No.1**：把玩法开关写成 multi_compile ——`multi_compile _ LEVEL1 LEVEL2 LEVEL3 LEVEL4`，本来只有少数组合真被用，却全量进包。**正确**：`shader_feature` 或更聪明的方案（见第3节）。

**误用事故 No.2**：shader_feature 的"被使用"**你从未主动声明**——你的美术在编辑器里勾选过，标记进了材质；但**通过脚本 `EnableKeyword` 动态打开**的组合，构建器不知道它在用 → **真机上变体缺失 → 物体紫色**（Missing shader）。必须用 **ShaderVariantCollection** 显式登记。

## 3. 变体爆炸：算一笔账

一个"功能齐全"的 URP 光照 shader（手写版）常见维度：

```
阴影        ×4   (无/有阴影/无+LPPV/有+LPPV)
光源数      ×3   (0/1/2 逐像素)
雾          ×4   (无/线/指/高度)
LIGHTMAP    ×4   (无/LIGHTMAP/SH/LPPV)
细节贴图    ×2
自发光      ×2
Instancing  ×2
遮挡预通道  ×2
→ 4×3×4×4×2×2×2×2 = 12,288 个变体
```

一个 shader 一万多变体，全编译：**每个变体×每个平台×每 Pass**——编译几小时、包体几个 GB、运行时首次加载全量哈希检索。这不是虚构的例子，是无数真实项目躺过的坑。内置管线（`Runtime/Shaders/` 里的官方 shader 家族）正是用极多 multi_compile 维度换"编辑器全场景兼容"，也因此体积巨大。

## 4. 治理工具箱

### 4.1 源码层：少开维度

- **能用 if 别用编译**：只影响 3~4 个 ALU 的功能，写成普通 if 或 lerp，不配当关键词（变体换分支的规则：**分支很重才值得编译期展开**）；
- **合并语义维度**：`_GLOW_STRENGTH` 用**浮点参数**（连续值）而不是 `_LEVEL1 _LEVEL2` 关键词（离散）；引擎自己的 FOG 就是"必开维度但只有一次采样+混合"的反例教材；
- **子着色器拆分**：把"高级功能"放进另一个 SubShader/pass，按能力平台选择，比每功能一个关键词省。

### 4.2 声明层：用局部与剔除

- `shader_feature_local`：**不进全局关键词命名空间**，编译范围限于本 shader（省编译、防名字冲突）——**默认写法建议**；
- `multi_compile_instancing` 等引擎提供"按需"声明（未启用 Instancing 的场景不产生维度）；
- `dynamic_branch`（URP 13+）：显式告诉编译器"这里要真分支，别展开"。

### 4.3 构建层：剥掉用不到的

- **Project Settings → Graphics Shader Stripping**（按管线配置）：光照模式（关掉的 Pass 类型整组剥）、雾、Instancing 的全剥开关；
- **IPreprocessShaders / IPreprocessBuild**（C# 接口）：自定义剔除回调——**最强大的武器**，可以按"当前项目内容"逐变体判断要不要（如"这个 demo 只用主光照，剥掉所有 FORWARD_ADD"）；
- **ShaderVariantCollection 记录**：编辑器 Project 窗口里"记录真用到的组合"（Save to asset），构建时以此为 shader_feature 的白名单。

### 4.4 运行时层：预暖

留下的变体在**Loading 画面里 WarmUp**（`ShaderVariantCollection.WarmUp()`），把"运行时首编卡顿"消灭在加载期。Preloaded Shaders 列表同理。

## 5. 团结引擎的本地化补充

团结/Unity 系里，`Runtime/Shaders/Keywords/` 是关键词系统的心脏（`ShaderKeywordSet` 等）；变体记录/剔除的资产管线在编辑器侧。团结附带的 **`com.unity.shaderanalysis` 包**（Packages 目录可见）提供构建期 shader 分析——帮助你回答"我的包里到底装了多少变体、谁贡献的"。大型项目应把"变体审计"纳入例行流程（CI 里检查包体变体数增量）。

> ⚠️ **紫色物体全家桶速查**：真机/构建后物体变紫 = 该组合的变体缺失。原因依次排查：① shader_feature 组合没登记（SVCC）；② 被剥变体的 Pass 在真机被管线请求了（自定义 RendererFeature 请求了被剥的 LightMode）；③ 平台能力不满足 target 声明（无可用 SubShader）。

---

## 小结

- 变体 = 关键词全排列的预编译产物，$V=\prod|K_i|$，爆炸是指数级；
- multi_compile 全打包（引擎用），shader_feature 按需打包（玩法用，要登记）；
- 治理四层：源码少开维度、local 声明、构建剥离（SVCC + IPreprocessShaders）、运行时预暖；
- 变体审计应成为大型项目的常规流程。
