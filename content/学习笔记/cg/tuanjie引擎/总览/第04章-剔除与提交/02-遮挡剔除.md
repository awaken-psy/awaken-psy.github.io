# 02 - 遮挡剔除

> 阅读时间：约 30 分钟
> 关键词：遮挡剔除、Occlusion Portal、Hi-Z、 baked 剔除

## 你将学到什么

- 团结/Unity 的 Occlusion Culling 窗口：怎么用、什么时候值得

## 1. 视锥体剔除的盲区

视锥体剔除只回答"在不在视野范围内"。但"在范围内"≠"看得见"：

```
                  ┌────────┐
   视锥体 →       │ 房间A   │ ← 10 个高模物体在里面
                  │ ██████ │
                  │ 房间B   │ ← 完全被房间A的外墙挡住
                  └────────┘
```

城市场景里，一条街看过去，视锥内可能有 500 栋楼，而你真正只看得到面前 3 栋楼的外墙。剩下 497 栋全部被挡住——**它们通过了视锥体剔除，然后每个都走了完整的合批/绘制流程，贡献的像素数 = 0**（被 Early-Z 挡住，PS 白跑或被 Early-Z 拦截）。

遮挡剔除回答：

> "有没有一堵'确定挡住它'的墙？有 → 提前扔掉，别等 GPU。"

注意与 Early-Z 的分工：**Early-Z 在 GPU 端"画了才发现被挡"（可能白跑 VS/光栅化），遮挡剔除在 CPU 端"预判被挡，直接不画"**。前者是最后一道保险，后者是主动省工。

## 2. 两大流派

### 2.1 预烘焙（团结/Unity Occlusion Culling 采用）

原理：把场景中"大的、实的、不会动的"物体标记为 **Occluder（遮挡体）**；小的、碎的、可能动的标记为 **Occludee（被遮挡体）**。编辑器里**离线**做两件事：

1. 从空间里一系列"视点单元"出发，对 Occluder 做可见性预计算（PVS 预计算可见集思想：把空间切成格子，记录每个格子里哪些物体"从这看必然不可见"）；
2. 运行时：查表——"相机在这个格子 → 这些物体必然被挡 → 直接剔除"。

```
编辑期:  场景 → 体素化/单元格 → 从每个单元做遮挡传播 → 烘焙 PVS 数据
运行期:  相机位置 → 找所在单元格 → 查表剔除 → 剩下的走视锥体剔除
```

**优点**：运行时几乎零成本（查表）。**代价**：烘焙数据占内存与包体；烘焙期间要求场景大件尽量静态；烘焙质量高度依赖"Occluder 选得好不好"（外墙用 Occluder，桌上的杯子显然是 Occludee）。

**团结/Unity 实践**（Window → Occlusion Culling 窗口）：
- 只对有 `Renderer` 的静态物体生效，烘出来的数据随场景保存；
- **室内/街区类**场景收益巨大（10 倍级物体数下降）；**开阔野外**（没有大遮挡物）收益≈0，白花包体；
- 物体动了、门开了——烘焙数据不会自动更新，动态遮挡需自己做（或用下节的运行时方案）。

### 2.2 运行时（GPU Hi-Z 剔除，现代方向）

不烘焙，每帧用 GPU 实时做：

1. 上帧深度图生成 **Hi-Z**（Hierarchical Z，深度逐层取 min 的 mip 链——第02章末提过）；
2. 本帧物体包围盒投影到屏幕 → 与 Hi-Z 对应层比较——"这物体最深点都比已画深度浅？→ 被挡，剔除"；
3. 剔除在 compute shader 里批量执行，输出"紧凑可见列表"给 CPU。

**优点**：动态场景完美适配（用上一帧的遮挡关系近似）、无烘焙数据。**代价**：延迟一帧的近似（镜头快速甩动会有极短暂"遮挡误判"，可见集偏大，无害）、需要现代 API/compute。这是 3A 引擎 GPU Driven Pipeline 的标配（第12章），团结引擎的 URP 暂未内置，自定义管线可自行实现。

## 3. 还有哪些"廉价遮挡"手段

新手值得知道的三种低成本变体：

| 手段 | 思路 | 典型场景 |
|---|---|---|
| **手动剔除开关** | 脚本按规则 `renderer.enabled = false` / 改 cullingMask | 3D 界面全屏时关场景渲染、切房间时关另一房间 |
| **Portal/单元可见性** | 手工划分"单元"，只有相邻单元间可通视 | 室内游戏（游戏逻辑控制，简单可靠） |
| **距离剔除 + 优先级** | 超过 X 距离直接不画 | 微信小游戏/开放世界远景（配合雾遮羞） |

引擎设置里的 **Culling Distance（按层配距离）** 就是最后一种的产品化：美术不可见的远景层提前全关。

## 4. 何时引入遮挡剔除：决策树

```
场景里有大型实体遮挡物吗？（楼、山、墙、舱壁）
├─ 没有（太空/海面/竞技场）→ 不值得上，专心做视锥体剔除+LOD
└─ 有
   ├─ 结构固定（烘焙后不会变）？ → 用引擎 Occlusion Culling 烘焙
   └─ 结构动态（可破坏/开关门/流式加载） → 脚本控制可见集 / 自研 Hi-Z
```

> ⚠️ **烘不出效果的最常见原因**：整个场景只勾了 Occludee 没勾 Occluder（没有"挡别人的墙"，自然烘不出东西）；或把小物件全标成 Occluder（烘焙慢 + 数据爆炸）。**Occluder = 少而大而实，Occludee = 多而小而动**。

> 📁 **源码指引**：烘焙数据与运行时查询集成在 `Runtime/Graphics/` 的剔除相关代码与 `Modules/` 侧遮挡管理；引擎核心的运行时剔除查询配合 `ScriptableCulling.cpp`。URP 侧每个相机/Pass 拿到的 `CullingResults` 已经包含遮挡剔除结果——管线无感知。

## 小结

- 遮挡剔除 = 视锥体剔除的补集：处理"视锥内但被挡"的物体；
- 预烘焙流派（引擎 Occlusion Culling）：离线 PVS 查表，室内场景神器；
- 运行时流派（Hi-Z）：每帧 GPU 深度判挡，动态友好，GPU Driven 时代标配；
- 决策三问：有大遮挡物吗？结构固定吗？产出配得上烘焙成本吗？

## 自测问题

1. Early-Z 和遮挡剔除都在处理"被挡住的物体"，区别是什么？（哪个阶段、谁出成本）
2. 为什么 Hi-Z 用"深度取 min"而不是平均？（提示：保守判定，与"宁多勿漏"原则对照）
3. 室外开阔场景用烘焙遮挡剔除，会得到什么？（用决策树回答）
4. 镜头快速旋转时 Hi-Z 剔除为什么"可能多画但不会漏画"？
