# 11 并行性表现与性能指标

> 同一个 kernel，只改 Block 的 `(x, y)` 配置，看哪个最快，用 nvprof 分析为什么。
> 关联：[[学习笔记/cg/cuda/cuda_freshman/10-资源分配与延迟隐藏与占用率.md|10 资源分配、延迟隐藏与占用率]] · [[学习笔记/cg/cuda/cuda_freshman/06-CUDA性能分析工具.md|06 CUDA 性能分析工具]]

---

## 1. 实验设置

8192×8192 的矩阵加法，每个元素就是 `C = A + B`：

```cpp
__global__ void sumMatrix(float *MatA, float *MatB, float *MatC, int nx, int ny)
{
    int ix = threadIdx.x + blockDim.x * blockIdx.x;
    int iy = threadIdx.y + blockDim.y * blockIdx.y;
    int idx = ix + iy * ny;
    if (ix < nx && iy < ny)
        MatC[idx] = MatA[idx] + MatB[idx];
}
```

通过命令行参数传不同的 `dimx`、`dimy`：

```bash
./simple_sum_matrix 32 32   # block = (32, 32) = 1024 线程
./simple_sum_matrix 16 16   # block = (16, 16) = 256 线程
./simple_sum_matrix 64 2    # block = (64, 2)  = 128 线程
```

---

## 2. 实验 1：不同 Block 大小的耗时

| blockDim | 总线程/Block | 耗时 (s) |
|---|---|---|
| (32, 32) | 1024 | **0.008304** ← 最快 |
| (32, 16) | 512 | 0.008332 |
| (16, 32) | 512 | 0.008341 |
| (16, 16) | 256 | 0.008347 |
| (16, 8) | 128 | 0.008351 |
| (8, 16) | 128 | 0.008401 |

**发现**：同样是 512 线程/Block，`(32,16)` 比 `(16,32)` 快。说明不仅 Block 大小重要，**x/y 怎么分配也有影响**。

---

## 3. 实验 2：用 nvprof 看占用率

```bash
nvprof --metrics achieved_occupancy ./simple_sum_matrix 32 32
```

| blockDim | 耗时 (s) | 占用率 |
|---|---|---|
| (32, 32) | **0.008304** ← 最快 | 0.814 ← 最低 |
| (16, 16) | 0.008347 | 0.876 ← 最高 |
| (16, 8) | 0.008351 | 0.876 |

> [!warning] 关键发现
> 占用率最高的不是最快的，占用率最低的反而最快！
> 印证了 [[学习笔记/cg/cuda/cuda_freshman/10-资源分配与延迟隐藏与占用率.md|10 资源分配、延迟隐藏与占用率]] 中的结论：**占用率高不等于一定快**。

## 4. 三个核心性能指标

### 内存吞吐量（gld_throughput）

**实际每秒从显存搬了多少数据**，单位 GB/s。

```
gld_throughput = 实际搬运的数据量 / 执行时间

例：60 GB/s 表示 GPU 每秒从显存读取了 60 GB 的数据
```

### 全局加载效率（gld_efficiency）

**搬过来的数据里，有多少是线程真正需要的。**

```
gld_efficiency = 线程请求的数据量 / 硬件实际搬运的数据量 × 100%

例：100% 表示搬过来的每字节都有用
    50% 表示搬了一堆没用的数据，浪费了一半带宽
```

为什么会搬没用的数据？因为 GPU 内存是**按块读取**的（最小 128 字节 / 一个缓存行），不是你要几个字节就搬几个字节：

```
线程 0 要读 MatA[0]    ← 4 字节（float）
硬件实际读取：          ← 128 字节（一个缓存行）

如果线程 1~31 恰好要读 MatA[1]~MatA[31]
  → 128 字节全用上了 → 效率 100%

如果只有线程 0 要读，其他线程不读
  → 128 字节只用了 4 字节 → 效率 3.1% → 浪费
```

> [!tip] 类比
> 内存吞吐量 = 快递车每小时实际运了多少货（吨/小时）
> 全局加载效率 = 运来的货里有多少是你订的，有多少是凑数的

### 两者的关系

```
有效吞吐量 = gld_throughput × gld_efficiency

吞吐量高 + 效率高 = 最好
吞吐量高 + 效率低 = 浪费带宽（搬了很多没用的）
吞吐量低 + 效率高 = 带宽没吃满（搬的太少）
```

### 如何提高加载效率

让相邻线程访问相邻的内存地址（连续访问）：

```
线程 0 读 data[0]，线程 1 读 data[1]，线程 2 读 data[2]...
→ 一条缓存行里的数据全被用上 → 效率 100%
```

这叫 **coalesced memory access（合并内存访问）**，是 CUDA 优化的核心技巧之一。

---

## 5. 实验 3：用 nvprof 看内存吞吐量

```bash
nvprof --metrics gld_throughput ./simple_sum_matrix 32 32
```

| blockDim | 耗时 (s) | 占用率 | 内存吞吐量 (GB/s) |
|---|---|---|---|
| (32, 32) | **0.008304** | 0.814 | **60.27** ← 最高 |
| (16, 16) | 0.008347 | 0.876 | 59.97 |
| (8, 16) | 0.008401 | 0.857 | 59.44 |

**发现**：`(32,32)` 虽然占用率低，但内存吞吐量最高，综合下来最快。

---

## 6. 实验 4：全局加载效率

```bash
nvprof --metrics gld_efficiency ./simple_sum_matrix 32 32
```

所有配置的加载效率都是 100%——现代 GPU + 编译器优化已经解决了老设备上的内存加载效率问题。

> [!info] 博客中提到的老设备问题
> 书上说 `blockDim.x` 过小（小于 32）会影响加载效率。但在现代机器上已经不存在这个问题了——硬件和编译器的进步让这个优化点失效了。

---

## 7. 实验 5：极端配置 — 内层维度很小

故意把 `blockDim.x` 设得非常小（2、4、8）：

| blockDim | 总线程 | 耗时 (s) | 占用率 |
|---|---|---|---|
| (64, 2) | 128 | **0.008391** ← 最快 | 0.889 |
| (64, 4) | 256 | 0.008411 | 0.866 |
| (128, 2) | 256 | 0.008454 | 0.893 ← 最高 |
| (256, 2) | 512 | 0.008468 | 0.859 |

**发现**：
- `(64,4)` 和 `(128,2)` 总线程都是 256，但效率不同 → **x/y 分配方式本身影响性能**
- 占用率最高的 `(128,2)` 不是最快的 → **单一指标不能决定性能**

## 8. 影响性能的因素总览

```
最终性能
    ↑
    ├── 占用率（活跃 Warp 数）       ← 提供更多 Warp 隐藏延迟
    │     ↑ 受限于：
    │     ├── 寄存器用量（每线程用越多 → 能驻留 Warp 越少）
    │     ├── 共享内存用量（每 Block 用越多 → 能驻留 Block 越少）
    │     └── Block 数量上限（架构限制）
    │
    ├── 内存吞吐量（GB/s）          ← 数据搬运的实际速度
    └── 全局加载效率（%）            ← 有效数据占总请求的比例
    
    这些因素互相影响，没有单一指标能直接决定最终性能
```

### 寄存器如何影响性能

寄存器是 SM 上的有限资源，**不是性能指标，而是影响占用率的根本原因**：

```
SM 有 65536 个寄存器

每线程用 40 个寄存器 → 65536 / 40 = 1638 线程 → 51 Warp → 占用率 100%
每线程用 80 个寄存器 → 65536 / 80 = 819 线程  → 25 Warp → 占用率 52%

占用率低 → 驻留 Warp 少 → 隐藏延迟能力弱 → 性能下降
```

用 ncu 查看寄存器使用量：

```bash
ncu --metrics launch__registers_per_thread ./your_program
```

| 性能指标 | 类型 | nvprof/ncu 命令 |
|---|---|---|
| `achieved_occupancy` | 占用率 | `--metrics achieved_occupancy` |
| `gld_throughput` | 内存吞吐量 | `--metrics gld_throughput` |
| `gld_efficiency` | 加载效率 | `--metrics gld_efficiency` |
| `registers_per_thread` | 每线程寄存器用量 | `--metrics launch__registers_per_thread` |

> [!warning] 核心结论
> **没有任何单一指标能直接决定性能。** 占用率高不一定快，吞吐量高不一定快，必须综合平衡多个指标。最终还是要靠**实际计时**来验证。寄存器用量是占用率的根源——寄存器用得多 → 占用率低 → Warp 少 → 隐藏延迟能力弱。
