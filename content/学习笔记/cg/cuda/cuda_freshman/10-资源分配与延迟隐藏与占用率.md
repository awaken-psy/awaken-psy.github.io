## 1. 资源分配 — SM 是个固定大小的工厂

把一个 SM 想象成一个**车间**，里面有固定的资源：

```
SM 车间有：
  ├── 65536 个寄存器      ← 每个线程要分一些
  ├── 48 KB 共享内存      ← 每个 Block 要分一些
  ├── 48 个 Warp 名额     ← 最多同时放 48 组工人
  └── 计算单元（CUDA Core）← 干活的机器
```

### 资源不够分给所有人

```
1 个 Block = 256 线程 = 8 个 Warp

如果每个线程用 40 个寄存器：
  1 个 Block 需要 256 × 40 = 10240 个寄存器
  SM 有 65536 → 能放 65536 / 10240 = 6 个 Block
  → 6 × 8 = 48 个 Warp → 占满名额，占用率 100%

如果每个线程用 80 个寄存器：
  1 个 Block 需要 256 × 80 = 20480 个寄存器
  SM 有 65536 → 能放 65536 / 20480 = 3 个 Block
  → 3 × 8 = 24 个 Warp → 只占一半，占用率 50%
```

> [!warning] 寄存器用得多 → 能放的 Warp 少 → 占用率低 → 性能差
> 如果一个 Block 需要的资源超过 SM 能提供的，kernel **根本无法启动**，直接报错。

### Warp 的三种状态

一个 Warp 在 SM 上的生命周期：

```
排队等候（未激活）
    │ SM 有空位了
    ▼
进入 SM，分配好资源（活跃）
    │
    ├── 准备就绪（符合条件的 Warp）  ← 数据齐了，可以执行
    │       │ 调度器选到它
    │       ▼
    │   正在执行（选定的 Warp）      ← 这个周期正在跑
    │       │ 遇到等待（如读内存）
    │       ▼
    └── 阻塞中（阻塞的 Warp）       ← 在等数据，暂时不能动
            │ 数据到了
            ▼
        回到"准备就绪"               ← 重新排队等调度
```

> [!info] Warp 一旦进入 SM，就不会离开，直到执行完毕。等数据时也不离开，而是切到别的 Warp 执行。这就是延迟隐藏的基础。

## 2. 延迟隐藏 — GPU 快的根本原因

### 什么是延迟

```
算术延迟：10~20 周期   ← 加减乘除等运算出结果的时间
内存延迟：400~800 周期  ← 数据从显存搬到寄存器的时间
```

如果只有一个 Warp，SM 在等待期间**什么都不干**，纯浪费。

### 延迟隐藏的原理

```
只有一个 Warp（浪费时间）：

时间 ──→
Warp 0:  [计算] [等......800周期......] [继续计算]
                          ↑
                   SM 空闲 800 周期，纯浪费

有多个 Warp（切换执行，不浪费）：

时间 ──→
Warp 0:  [计算] [等.................] [继续]
Warp 1:         [计算] [等...........] [继续]
Warp 2:                [计算] [等....] [继续]
Warp 3:                       [计算] [等] [继续]
                ↑
        Warp 0 等数据时，SM 不闲着，切到 Warp 1 执行
        Warp 1 等数据时，切到 Warp 2
        ... 交替执行，SM 始终满载
```

### 为什么 Warp 切换零开销

CPU 线程切换要保存/恢复寄存器、上下文，开销很大。

GPU 的所有 Warp 都驻留在 SM 上，各自的寄存器一直在那：

```
SM 上的寄存器：
┌─────────────────────────────────────────┐
│ Warp 0 的寄存器  │ Warp 1 的寄存器  │ Warp 2 的寄存器  │ ...
└─────────────────────────────────────────┘
        ↑                   ↑                   ↑
     刚执行完            下一个执行           再下一个

调度器只是换一个指针指向谁，数据不动，零开销。
```

### Little 法则 — 需要多少 Warp 才够

$$
\text{所需 Warp 数} = \text{延迟} \times \text{吞吐量}
$$

```
算术延迟 = 20 周期，SM 每周期执行 1 个 Warp 的指令
所需 Warp = 20 × 1 = 20 个
所需线程 = 20 × 32 = 640 个线程

意思：至少 640 个线程同时在 SM 上，
才能保证每个周期都有 Warp 可执行，SM 不闲着。
```

> [!info] 带宽 vs 吞吐量
> - **带宽**：理论峰值，比如 144 GB/s
> - **吞吐量**：实际达到的值
> - 目标是让吞吐量尽可能接近带宽

### 两种并行方式

| 方式 | 全称 | 原理 |
|---|---|---|
| **ILP** | 指令级并行 | 一个线程内有多条独立指令可以同时执行 |
| **TLP** | 线程级并行 | 多个线程同时执行，Warp 之间切换隐藏延迟 |

## 3. 占用率（Occupancy）

### 定义

```
占用率 = 活跃 Warp 数 / SM 最大 Warp 数
```

RTX 3060 Ti 每 SM 最多 48 个 Warp：

```
活跃 48 个 Warp → 占用率 100%
活跃 24 个 Warp → 占用率 50%
活跃 12 个 Warp → 占用率 25%
```

### 三个制约因素（取最严格的那个）

**① 寄存器限制**

```
SM 有 65536 寄存器

每线程用 40 个 → 65536 / 40 = 1638 线程 = 51 Warp → 受上限 48 限制 → 100%
每线程用 80 个 → 65536 / 80 = 819 线程  = 25 Warp → 占用率 52%
```

**② 共享内存限制**

```
SM 有 48 KB 共享内存

每 Block 用 48 KB → 只能放 1 个 Block
如果 Block 有 256 线程 = 8 个 Warp → 占用率 8/48 = 17%
```

**③ Block 数量限制**

```
SM 最多同时放 N 个 Block（架构相关，Ampere 为 16）
```

### Block 大小怎么选

| Block 大小 | 问题 |
|---|---|
| 太小（32 线程 = 1 Warp） | Block 数量到上限时，资源可能没用完，占用率受限 |
| 太大（1024 线程 = 32 Warp） | 一个 Block 占满资源，SM 只能放 1 个 Block |
| 适中（128~256 线程） | 多个 Block 共享资源，通常占用率较高 |

> [!tip] 占用率高不等于一定快
> 占用率高只是提供了更多的 Warp 来隐藏延迟。如果 kernel 本身没有延迟需要隐藏（比如纯计算无内存访问），占用率 50% 也可能跑满。关键是**有足够的 Warp 来隐藏延迟**。

### 如何查看占用率

```bash
# ncu 查看
ncu --metrics achieved_occupancy ./your_program
```

## 4. 同步

### 两个层级

| 层级 | 方法 | 说明 |
|---|---|---|
| Block 内 | `__syncthreads()` | 同一 Block 内所有线程到齐再继续 |
| 系统级 | kernel 执行完成 | 所有 Block 都跑完，CPU 拿回控制权 |

### `__syncthreads()` 示例

```cpp
__shared__ float shared[256];
shared[threadIdx.x] = data[threadIdx.x];
__syncthreads();  // 等所有人写完
float v = shared[255 - threadIdx.x];  // 安全读取别人写的数据
```

```
线程 0:  写 shared[0]    ──→  到达屏障，等...
线程 1:  写 shared[1]    ──→  到达屏障，等...
...
线程 255: 写 shared[255] ──→  到达屏障
                                ↓
                           全部到齐！继续执行
```

### 为什么 Block 间不能同步

```
SM 0:  Block 0 正在执行  ──→  想等 Block 1 的结果
SM 1:  Block 1 还在排队  ──→  根本没开始

→ Block 0 等一个还没启动的 Block → 死等
```

> [!warning] Block 是分批执行的，有些还在排队。唯一的全局同步是 kernel 执行完毕。

## 5. 可扩展性

```
GPU A: 38 个 SM → 1000 个 Block 分 3 批执行 → 耗时 T
GPU B: 76 个 SM → 1000 个 Block 分 2 批执行 → 耗时约 T/2
```

Block 之间互相独立（不通信、不等待），SM 越多，并行度越高。CUDA 驱动自动分配，程序员不需要改代码。

> [!warning] 如果 Block 之间有数据依赖，SM 再多也得排队，无法线性扩展。
