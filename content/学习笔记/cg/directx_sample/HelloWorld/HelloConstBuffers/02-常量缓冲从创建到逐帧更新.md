# 常量缓冲：从创建到逐帧更新

上一节：[[学习笔记/cg/directx_sample/HelloWorld/HelloConstBuffers/01-为什么需要常量缓冲.md|为什么需要常量缓冲]]  
索引：[[学习笔记/cg/directx_sample/HelloWorld/HelloConstBuffers/00-HelloConstBuffers学习索引.md|HelloConstBuffers 学习索引]]

这一篇把资源、描述符、根签名、逐帧更新、命令绑定、着色器读取和同步安全放在同一条因果链中理解。

## 一、先分清五个角色

```text
SceneConstantBuffer
    CPU 与 HLSL 共同遵守的数据布局

m_constantBuffer
    真正保存 256 字节数据的 GPU 资源

CBV
    用 GPU 地址和大小描述这块资源

m_cbvHeap
    保存 CBV，并允许 GPU 在绘制时访问它

根签名与根描述符表
    规定着色器从哪个绑定槽位找到这个 CBV
```

资源本身只是一块内存。只创建 `m_constantBuffer`，并不会自动让着色器知道它在哪里；CBV、描述符堆和根签名共同建立了可访问路径。

## 二、创建 shader-visible 描述符堆

`LoadPipeline()` 创建只容纳一个描述符的堆：

```cpp
D3D12_DESCRIPTOR_HEAP_DESC cbvHeapDesc = {};
cbvHeapDesc.NumDescriptors = 1;
cbvHeapDesc.Flags = D3D12_DESCRIPTOR_HEAP_FLAG_SHADER_VISIBLE;
cbvHeapDesc.Type = D3D12_DESCRIPTOR_HEAP_TYPE_CBV_SRV_UAV;
m_device->CreateDescriptorHeap(&cbvHeapDesc, IID_PPV_ARGS(&m_cbvHeap));
```

这里还没有创建常量缓冲，也没有写入 CBV。它只是先准备一块可以保存 CBV、并能在绘制时绑定给 GPU 的描述符空间。

`SHADER_VISIBLE` 是关键边界：RTV 描述符堆由 CPU 在录制命令时取句柄使用，而这个 CBV 堆需要进一步让着色器经由根描述符表访问。

## 三、根签名声明绑定契约

本例的根签名只有一个根参数：

```cpp
ranges[0].Init(
    D3D12_DESCRIPTOR_RANGE_TYPE_CBV,
    1,
    0,
    0,
    D3D12_DESCRIPTOR_RANGE_FLAG_DATA_STATIC);

rootParameters[0].InitAsDescriptorTable(
    1,
    &ranges[0],
    D3D12_SHADER_VISIBILITY_VERTEX);
```

当前主线只需要读出三个事实：

1. 描述符类型是 CBV；
2. 数量是一个，从常量寄存器 `b0` 开始；
3. 只有顶点着色阶段需要访问它。

HLSL 的声明与之对应：

```hlsl
cbuffer SceneConstantBuffer : register(b0)
```

根签名在这里规定的是“接口”，并没有绑定某个具体资源。真正把本例的 CBV 接到根参数 0，要等录制每帧命令时完成。

## 四、创建允许 CPU 写入的资源

`LoadAssets()` 使用 UPLOAD 堆创建缓冲资源：

```cpp
const UINT constantBufferSize = sizeof(SceneConstantBuffer);

m_device->CreateCommittedResource(
    &CD3DX12_HEAP_PROPERTIES(D3D12_HEAP_TYPE_UPLOAD),
    D3D12_HEAP_FLAG_NONE,
    &CD3DX12_RESOURCE_DESC::Buffer(constantBufferSize),
    D3D12_RESOURCE_STATE_GENERIC_READ,
    nullptr,
    IID_PPV_ARGS(&m_constantBuffer));
```

选择 UPLOAD 堆的直接原因是 CPU 每帧都要写入位移。它让 CPU 可以映射这块资源，GPU 则从中读取。

本例没有额外创建 DEFAULT 堆和复制命令，因为目标是突出少量动态数据的更新通路。这个选择不表示所有 GPU 数据都应长期放在 UPLOAD 堆；静态顶点、纹理和大量数据还要根据访问模式设计上传过程。

## 五、创建 CBV，把资源写进描述符堆

```cpp
D3D12_CONSTANT_BUFFER_VIEW_DESC cbvDesc = {};
cbvDesc.BufferLocation = m_constantBuffer->GetGPUVirtualAddress();
cbvDesc.SizeInBytes = constantBufferSize;

m_device->CreateConstantBufferView(
    &cbvDesc,
    m_cbvHeap->GetCPUDescriptorHandleForHeapStart());
```

CBV 记录两项核心信息：

- 从哪个 GPU 虚拟地址开始读取；
- 允许把多少字节当作常量缓冲读取。

`CreateConstantBufferView()` 的第二个参数是 CPU 描述符句柄，因为这一步由 CPU 把描述符写入堆中。到真正绑定根描述符表时，命令列表会改用同一描述符堆的 GPU 句柄。

## 六、长期 Map，而不是每帧 Map/Unmap

```cpp
CD3DX12_RANGE readRange(0, 0);
m_constantBuffer->Map(
    0,
    &readRange,
    reinterpret_cast<void**>(&m_pCbvDataBegin));

memcpy(
    m_pCbvDataBegin,
    &m_constantBufferData,
    sizeof(m_constantBufferData));
```

`readRange(0, 0)` 表示 CPU 不打算读取该资源。Map 成功后，示例把地址长期保存在 `m_pCbvDataBegin`，应用运行期间不必每帧反复 Map 和 Unmap。

初始化复制也很重要。构造函数通过 `m_constantBufferData{}` 把数据清零，创建资源后立刻复制一次，使第一次绘制前 GPU 已经能读到确定的 offset。

## 七、OnUpdate 只更新小块动态数据

```cpp
m_constantBufferData.offset.x += translationSpeed;

if (m_constantBufferData.offset.x > offsetBounds)
{
    m_constantBufferData.offset.x = -offsetBounds;
}

memcpy(
    m_pCbvDataBegin,
    &m_constantBufferData,
    sizeof(m_constantBufferData));
```

这段代码没有修改顶点缓冲，也没有录制绘制命令。它只完成两件事：

1. 在 CPU 侧计算本帧的新位移；
2. 把完整的 256 字节常量块复制到映射地址。

超过右边界后把 x 位移放回左边界，所以三角形会循环移动。`translationSpeed` 是每次更新增加的固定量，本例没有使用时间差，因此它是教学用的按帧移动，而不是完整的时间驱动动画系统。

## 八、录制命令时把 CBV 接到根参数 0

`PopulateCommandList()` 中的三步必须连起来看：

```cpp
m_commandList->SetGraphicsRootSignature(m_rootSignature.Get());

ID3D12DescriptorHeap* ppHeaps[] = { m_cbvHeap.Get() };
m_commandList->SetDescriptorHeaps(_countof(ppHeaps), ppHeaps);

m_commandList->SetGraphicsRootDescriptorTable(
    0,
    m_cbvHeap->GetGPUDescriptorHandleForHeapStart());
```

因果关系是：

```text
选择根签名
    ↓ 确定根参数布局
绑定 shader-visible 描述符堆
    ↓ 让 GPU 能解析这块描述符空间
让根参数 0 指向堆中的第一个 CBV
    ↓
CBV 给出常量缓冲的 GPU 地址与大小
    ↓
HLSL 的 b0 可以读取 offset
```

第一个参数 `0` 指根签名中的第 0 个根参数，不是 HLSL 寄存器号本身。这个根参数内部的描述符范围才声明从 `b0` 开始。

## 九、Draw 时怎样得到移动后的顶点

绘制调用仍然是：

```cpp
m_commandList->IASetVertexBuffers(0, 1, &m_vertexBufferView);
m_commandList->DrawInstanced(3, 1, 0, 0);
```

但顶点着色器现在同时拥有两种输入：

```text
顶点缓冲 position ─┐
                    ├─ VSMain → position + offset → 最终裁剪空间位置
常量缓冲 offset ───┘
```

```hlsl
result.position = position + offset;
```

像素着色器没有读取常量缓冲，它仍然只输出插值后的颜色。根参数因此被限制为顶点着色器可见，准确表达了本例的用途。

## 十、为什么重复写同一块缓冲目前是安全的

CPU 可能准备下一帧时，GPU 还在读取上一帧。如果此时直接覆盖同一块常量内存，GPU 就可能读到被提前修改的数据。

HelloConstBuffers 的处理方式很简单：每帧提交和 Present 后调用 `WaitForPreviousFrame()`，等待 GPU 完成本帧。下一轮 `OnUpdate()` 再写这块内存时，上一帧已经读完。

```text
CPU 写 offset
    ↓
提交并让 GPU 读取
    ↓
Fence 等待 GPU 完成
    ↓
CPU 才再次覆盖同一块内存
```

这种方式容易理解，但 CPU 与 GPU 基本串行。后续 HelloFrameBuffering 会使用按帧资源和更完整的 Fence 管理，让 CPU 在 GPU 处理前一帧时继续准备后续帧。

## 十一、HelloConstBuffers 完整流程

```text
OnInit
├─ LoadPipeline
│  ├─ 创建 RTV 描述符堆
│  └─ 创建 shader-visible CBV 描述符堆
│
└─ LoadAssets
   ├─ 创建根签名：根参数 0 → 一个从 b0 开始的 CBV
   ├─ 创建 PSO 和顶点缓冲
   ├─ 创建 256 字节 UPLOAD 常量缓冲
   ├─ 创建 CBV 并写入描述符堆
   ├─ 长期 Map 常量缓冲
   └─ 上传初始全零数据

每一帧
├─ OnUpdate
│  ├─ 修改 offset.x
│  └─ memcpy 到映射的常量缓冲
│
└─ OnRender
   ├─ PopulateCommandList
   │  ├─ 绑定根签名
   │  ├─ 绑定 CBV 描述符堆
   │  ├─ 根参数 0 指向 CBV
   │  ├─ 绑定顶点缓冲
   │  └─ DrawInstanced
   │      └─ VSMain 读取 position 与 offset
   ├─ 提交主命令列表
   ├─ Present
   └─ Fence 等待，保护下一次常量缓冲写入
```

## 最终结论

> HelloConstBuffers 没有通过改写三角形几何来制造运动，而是建立了“CPU 动态数据 → 常量缓冲资源 → CBV → 根描述符表 → HLSL b0”的完整绑定通路；当前逐帧 Fence 等待保证同一块常量内存可以安全复用，并为下一阶段的帧资源管理留下了清晰问题。
