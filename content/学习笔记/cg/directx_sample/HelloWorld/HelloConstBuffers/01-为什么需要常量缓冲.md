## 先看真正发生变化的东西

HelloConstBuffers 仍然绘制同一个三角形：

- 三个顶点的原始位置没有改变；
- 顶点颜色没有改变；
- 图元仍然是三角形列表；
- 绘制调用仍然读取三个顶点；
- 每帧真正变化的只有一个水平方向位移。

因此，这一阶段不是重新学习怎样绘制三角形，而是解决下面的问题：

> CPU 怎样把一份体积很小、每帧变化的数据交给正在执行顶点着色器的 GPU？

如果每次移动都去改写三个顶点的位置，那么“几何本身是什么”和“这一帧把几何放在哪里”就会混在同一份顶点数据中。常量缓冲让二者分开：

```text
顶点缓冲：保存不变的局部几何
常量缓冲：保存本帧使用的位移
顶点着色器：读取二者并得到最终位置
```

这里的“常量”不是指应用运行期间永远不变，而是指一次着色器读取过程中，它作为统一输入供一批着色器调用使用。CPU 完全可以在下一帧写入新的值。

## 与 HelloBundles 的区别

HelloBundles 和 HelloConstBuffers 都从“什么会变”开始划分职责，但对象不同：

| 示例 | 保持稳定的部分 | 每帧变化的部分 | 解决的问题 |
|---|---|---|---|
| HelloBundles | 一段绘制命令 | 当前后台缓冲区相关命令 | 怎样复用已经录好的命令 |
| HelloConstBuffers | 顶点和主要绘制流程 | 传给着色器的位移数据 | 怎样更新 GPU 每帧读取的数据 |

Bundle 保存的是 GPU 命令记录；常量缓冲保存的是着色器输入数据。两者不能互相替代。

## CPU 和 HLSL 必须遵守同一份数据契约

C++ 侧定义：

```cpp
struct SceneConstantBuffer
{
    XMFLOAT4 offset;
    float padding[60];
};
```

HLSL 侧定义：

```hlsl
cbuffer SceneConstantBuffer : register(b0)
{
    float4 offset;
    float4 padding[15];
};
```

两边采用的写法不同，但大小一致：

```text
C++：  XMFLOAT4       16 字节
       float[60]     240 字节
                      ───────
                      256 字节

HLSL： float4          16 字节
       float4[15]     240 字节
                      ───────
                      256 字节
```

CPU 只是在一段内存中写入字节，GPU 会按照 HLSL 声明解释这些字节。因此，两端必须对字段顺序、类型和布局形成一致约定，否则程序可能正常编译，却在 GPU 端读到错误的值。

## 为什么补到 256 字节

D3D12 创建常量缓冲视图时，视图大小必须按 256 字节对齐。本例真正使用的 `offset` 只有 16 字节，但仍然需要把整个常量块补到 256 字节。

头文件中的检查：

```cpp
static_assert(
    (sizeof(SceneConstantBuffer) % 256) == 0,
    "Constant Buffer size must be 256-byte aligned");
```

它把运行时约束提前变成编译时约束。如果以后有人添加或删除字段却破坏了对齐，构建会立刻失败，而不是等到运行时才通过调试层发现问题。

需要区分两个概念：

- **结构体当前恰好占多少有效数据**：本例只有一个 16 字节位移；
- **CBV 必须覆盖的对齐空间**：本例为 256 字节。

padding 只是满足布局约束，不会进入着色计算。

## 位移为什么能移动整个三角形

顶点着色器执行三次，分别处理三个顶点。每次都读取同一个 `offset`：

```hlsl
result.position = position + offset;
```

三个顶点增加相同位移，因此它们之间的相对位置没有变化，最终表现为整个三角形一起平移。CPU 当前只更新 `offset.x`，所以移动方向是水平的。

## 这一节应记住什么

> 常量缓冲把“稳定的几何”与“每帧变化的着色器输入”分开；CPU 和 HLSL 通过一致的数据布局共享这份输入，而 D3D12 要求 CBV 大小按 256 字节对齐。
