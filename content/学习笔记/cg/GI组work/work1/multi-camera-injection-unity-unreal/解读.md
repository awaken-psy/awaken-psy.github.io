# 工作解读：为 Unity / Unreal 游戏注入额外相机（引擎级方案）

> 本文件是对 `multi-camera-injection-unity-unreal.md` 的解读分析，撰写日期 2026-07-07。

---

## 1. 这项工作在做什么

**核心目标**：给一个已经打包好的 Unity 或 Unreal 游戏（Android / Windows），在不改源码、不重新编译游戏的前提下，通过运行时注入"挂载"若干额外的虚拟相机。这些相机跟随游戏主相机运动，各自独立渲染出不同视角的画面，用于生成多视角 / 深度 / 语义数据集。

**一句话概括**：利用游戏引擎自身的渲染管线，在运行时"合法地"创建第二、第三乃至第 N 个相机，让引擎替你做剔除、阴影、LOD 等全部重活，你只需要读回渲染结果落盘。

---

## 2. 为什么选引擎级注入而非图形 API 拦截

文档定位为"路线 A（引擎级注入）"，是相对于"路线 B（图形 API 拦截）"的方案选择。两者的根本差异在于**在哪一层动手**：

| 维度 | 引擎级注入（本文档） | 图形 API 拦截（路线 B） |
|---|---|---|
| 动手位置 | 引擎逻辑层（C# / UObject 反射） | GPU 绘制调用层（D3D/Vulkan hook） |
| 相机身份 | 引擎一等公民，完整渲染管线 | 外部拦截，只能复制已提交的 draw call |
| **剔除问题** | **无**——引擎为每个相机独立跑视锥剔除 | **有硬伤**——CPU 端剔除在 GPU 提交前已完成，附加相机偏移视角就会看到空洞 |
| 相机自由度 | 任意朝向、环绕、俯拍 | 仅限小基线、与主相机视锥高度重叠 |
| 视角相关效果 | 阴影 / 后处理 / 反射全部正确重算 | 复用主视角结果，不同程度失真 |
| 工程量 | 低（PoC 数天） | 高（每款游戏需逆向定位 constant buffer） |

**最关键的判断点**是"剔除空洞"问题。在图形 API 层面拦截时，主相机在 CPU 端就已经把视锥外、被遮挡、远距离的物体剔掉了，GPU 只收到"该画的"draw call。附加相机如果看向别处，那些被剔除的物体从没进过绘制流，画面上就是空洞。而引擎级注入创建的相机是引擎渲染循环中的正式成员，引擎会为它独立跑全套剔除和渲染流程，所以不会出现空洞。

文档的结论是：**目标一旦确认为 Unity/Unreal，引擎级注入即为默认方案；只有引擎未知或闭源时才回退到图形 API 拦截。**

## 3. Unity 落地路径解读

### 3.1 注入方式

文档推荐 **BepInEx** 或 **MelonLoader** 作为注入框架。这两个框架的共性是：

- 在进程启动早期加载托管插件
- 提供 Harmony 运行时方法补丁能力
- 对 IL2CPP 后端有 Il2CppInterop 支持（运行时生成托管代理程序集）

Unity 游戏的脚本后端分 Mono 和 IL2CPP 两种，影响注入难度：

- **Mono 后端**：最省事，可直接加载托管 DLL，反射调用引擎 API
- **IL2CPP 后端**：C# 被编译成原生代码，需通过 `global-metadata.dat`` 还原符号信息，BepInEx/MelonLoader 内置了这一能力

### 3.2 技术实现要点

核心代码骨架非常简洁——本质上就是：

1. `Camera.main` 找到主相机
2. `new GameObject` + `AddComponent<Camera>()` 创建附加相机
3. `cam.CopyFrom(main)` 继承 FOV / 近远平面 / 裁剪层等参数
4. 设 `targetTexture` 为 RenderTexture 做离屏渲染
5. 将附加相机挂为主相机的子物体（或世界锚点），设偏移
6. `cam.enabled = true` 让引擎自动把它纳入渲染队列

**关键洞察**：`enabled = true` 后不需要手动复制任何几何数据，Unity 的渲染管线会在每帧自动为这个相机独立做视锥剔除、阴影计算、LOD 选择。这是"无空洞"优势的技术来源。

### 3.3 渲染管线适配

文档特别提醒了渲染管线的差异：

- **Built-in RP**：`Camera` + `targetTexture` 直接可用，最简单
- **URP / HDRP（SRP）**：相机照常创建，但渲染由 `RenderPipelineManager` 统一调度。需要用 `beginCameraRendering` / `endCameraRendering` 回调来定制，或通过 `UniversalAdditionalCameraData` 配置

### 3.4 数据导出

- **同步读回**：`RenderTexture.active` + `ReadPixels` → PNG/EXR。简单但会 stall GPU，适合离线
- **异步读回**：`AsyncGPUReadback.Request` → 回调拿 `NativeArray` 落盘。不阻塞主线程，实时优选
- **深度**：设 `DepthTextureMode.Depth`，从 `_CameraDepthTexture` 取，导出时需按近远平面做反投影转线性深度
- **相机内外参**：`projectionMatrix` 和 `worldToCameraMatrix` 直接读出

## 4. Unreal 落地路径解读

### 4.1 注入方式

Unreal 是 C++ 原生引擎，没有 Mono 那样的托管层。注入本质是**通过 UObject 反射系统找到并调用引擎 API**。

- **UE4SS**（Lua + C++）：运行时脚本 mod 框架，封装好了 UObject 反射调用，首选
- **Dumper-7**：从内存 dump 出完整 SDK（偏移表），供写原生 C++ DLL 直接调用，最灵活但最重

### 4.2 核心方案：SceneCaptureComponent2D

文档明确推荐用 `USceneCaptureComponent2D` 而非额外的 `APlayerCameraManager`。原因在于 SceneCapture 是 UE 原生的"离屏相机"，专门把场景渲染到 RenderTarget，且能直接输出多种 G-buffer 通道：

| CaptureSource | 输出内容 |
|---|---|
| `FinalColorLDR` / `FinalColorHDR` | 最终画面（LDR/HDR） |
| `SceneDepth` | 深度真值 |
| `Normal` / `BaseColor` | G-buffer 通道 |
| 配合 Custom Depth / Stencil | 物体 ID / 语义分割 |

**这是 UE 相对 Unity 的一个显著优势**：一个 SceneCapture 可切换 CaptureSource 分别取 color / depth / normal；配合 Custom Depth Stencil 能给不同物体打 stencil 值，直接导出语义分割 / 实例 ID 真值——这对数据集来说是理想的数据来源。

### 4.3 运动绑定

每帧从 `PlayerCameraManager->GetCameraLocation() / GetCameraRotation()` 取主相机位姿作为基准，对每个附加 SceneCapture 施加偏移 / 环绕 / 固定机位变换。UE4SS 可 hook `Tick` 或每帧调用的 UFunction 来驱动。

## 5. 平台考量

### Windows

- 工具生态成熟，GPU 余量大，实时多相机可行
- **文档建议优先在 Windows 上做 PoC**

### Android

- 注入更难：Unity Mono 可用 BepInEx/MelonLoader Android 移植；IL2CPP 需处理 `libil2cpp.so` + `global-metadata.dat`，可用 LSPatch / Frida
- 常需重打包或 root，会破坏签名校验
- GPU 性能吃紧：实时建议 ≤1 个低分辨率附加相机
- **文档建议将 Android 定位为离线数据采集平台，不追求实时多路**

---

## 6. 分阶段落地路线

文档提出了 4 个阶段：

| 阶段 | 内容 | 预估时间 |
|---|---|---|
| 阶段 0 | 判引擎、平台、注入可行性 | 0.5 天 |
| 阶段 1 | 单个附加相机 PoC——验证"偏离主相机无空洞" | 1–2 天 |
| 阶段 2 | 相机运动绑定（环绕 / 跟随 / 固定机位） | 2–3 天 |
| 阶段 3 | 多相机 + 多通道（color + depth + normal + ID） | 1 周 |
| 阶段 4 | 数据集管线（内外参 + 时间戳，对标 NeRF/3DGS 格式） | 持续 |

**阶段 1 的验收标准特别值得注意**：除了看到第二视角画面，必须验证"朝向偏离主相机时无剔除空洞"——这是引擎路线相对于图形 API 路线的核心价值验证点。

---

## 7. 风险与约束

文档在 §7 诚实地列出了风险：

1. **反作弊 / 完整性校验**：注入行为极易触发 EAC/BattlEye/nProtect，建议只在单机 / 无反作弊游戏上做
2. **IL2CPP / pak 加密**：增加符号还原成本，但不改变机制可行性
3. **渲染管线适配**：Unity URP/HDRP、UE4 vs UE5（Nanite/Lumen）的细节差异需要在 PoC 前确认
4. **性能倍增**：每多一个附加相机 ≈ 多一遍剔除 + 渲染负载（近线性），实时 ≤1–2 个降分辨率相机
5. **法律 / 授权**：修改客户端、重打包、抓取渲染数据可能违反 EULA

## 8. 整体评价

### 8.1 方案合理性

这项工作的技术路线选择是合理的。引擎级注入将问题从"逆向 GPU 绘制流"降维到"调用引擎已有 API"，大幅降低了工程量和不确定性。核心论点——"引擎会为新相机独立做剔除"——在 Unity 和 Unreal 的架构上都是成立的。

### 8.2 关键优势

- **工程质量高**：利用引擎自身的渲染管线，不需要手动处理剔除、阴影、LOD 等复杂逻辑
- **数据质量有保障**：视角相关效果（阴影、后处理、反射）全部正确
- **可扩展性强**：从单相机到多相机、从 color 到多通道，路径清晰
- **UE 的语义真值能力突出**：Custom Depth Stencil 可直接产出语义分割 / 实例 ID，是数据集的理想来源

### 8.3 需要关注的实际挑战

- **注入框架的稳定性**：BepInEx/MelonLoader/UE4SS 对不同游戏版本的兼容性参差不齐，IL2CPP 游戏尤其需要逐个适配
- **性能现实**：实时多相机在桌面 GPU 上也非"免费"，需要量化单相机渲染开销来估算可行性
- **Android 落地难度**：文档虽提及但着墨较少，实际 Android 注入（尤其 IL2CPP + 无 root）的工程量远高于 Windows
- **数据集格式对齐**：阶段 4 提到"对标 NeRF/3DGS 格式"，但具体的元数据格式（COLMAP / transforms.json / KITTI 等）还需明确

### 8.4 与我们 Tuanjie 引擎源码的关系

我们手上有 Tuanjie 引擎（Unity 2022.3 fork）的完整源码。这意味着：
- 如果目标游戏是 Unity 引擎，我们对引擎内部的相机系统、渲染管线、剔除逻辑有完全的源码级理解
- 理论上甚至可以在引擎源码层面做更深层的修改（如自定义渲染 pass、深度导出等），而不依赖黑盒注入
- 但文档的场景是"给已打包的游戏注入相机"（不改源码），所以源码的价值更多在于理解引擎行为、辅助调试和验证
